# AGENTS

## Project

**BiClock (Bilibili 时钟)** — a small Manifest V3 browser extension that overlays the current time on top of the Bilibili video player. By default it shows **while in browser fullscreen and controls are visible**, because only real fullscreen avoids being covered by Bilibili's/browsers' own floating video toolbars; the user can turn off "仅全屏显示" to also show in non-fullscreen player modes. Loads directly as unpacked source; there is no build step, bundler, TypeScript, or test setup in this repo despite the parent directory being `TypeScript/`.

## Layout

- `manifest.json` — MV3 manifest. Content scripts `shared.js` + `biclock.js` (loaded in that order) run on `*://*.bilibili.com/video/*` and `*://*.bilibili.com/bangumi/*`. Declares `action.default_popup` → `popup.html`, `options_ui` → `options.html` (with `open_in_tab: true`, so the settings page opens as a full browser tab rather than a second popup), and `permissions: ["storage"]`. Includes `browser_specific_settings.gecko.id`, so the same package targets both Firefox and Chromium.
- `shared.js` — the single source of truth for logic shared between the popup, the options page, and the content script. Provides `DEFAULTS`, `THEME_STYLE_KEYS`, `THEME_CSS_KEYS`, `APPEARANCE_INLINE_KEYS`, `REMOVED_THEME_IDS`, `pad`, `formatTime`, `makeClockPart`, `hexToRgba`, `renderClockLayout(el, time, style, prefix)`, `applyHtmlTemplate(el, html, time)` + its helpers `splitPlaceholders` / `updateHtmlTemplateTime`, and `migrateRemovedTheme(config, onPersist)`. Loaded before `popup.js` (popup), before `options.js` (options page), and before `biclock.js` (content script) so its top-level `var`/`function` declarations are visible to the dependent script via the shared classic-script global — **no ES modules, no imports**. `THEME_STYLE_KEYS` (13 appearance keys) and `THEME_CSS_KEYS` (`customHtml` / `customHtmlEnabled` — the constant name is historical; it now covers only the HTML template snapshot keys since the custom CSS mode was removed) together define what a custom theme snapshots; only `options.js` consumes `THEME_CSS_KEYS`. `APPEARANCE_INLINE_KEYS` is the shared list of inline-style properties that `applyStyles()` / `applyToPreview()` wipe when HTML template mode is on (so the user's HTML template — including any inline `style` / `<style>` it carries — is the sole appearance source — see the Styling bullet below). The `prefix` arg to `renderClockLayout` namespaces child class names for the built-in layout branches: the popup preview, the options preview, and the content script all pass `'bpx-player-clock'` (so user CSS selectors hit identically in all three); theme-card samples pass `'clock'` to stay isolated from user CSS. `renderClockLayout` dispatches to `applyHtmlTemplate` first when `style.customHtmlEnabled && style.customHtml` is set — see the Styling bullet for the HTML template mode's distinct re-render contract.
- `biclock.js` — the content script (loaded after `shared.js`). Creates a `.bpx-player-top-clock` div, formats the time via shared helpers, and appends it to `.bpx-player-container`. The clock is **directly draggable in the real player**: holding left-button on the clock and moving the pointer sets `posX/posY` live (same edge-aligned math as the options-page preview, just using `.bpx-player-container.getBoundingClientRect()` instead of the banner's); on `mouseup` the final position is persisted to `chrome.storage.local` so the options preview stays in sync. `mousedown` on the clock calls `preventDefault()` + `stopPropagation()` so the drag does not trip Bilibili's own player click handlers (e.g. toggling the control bar). Display behavior is unchanged by dragging — the clock is still torn down by `stopTimer()` when `shouldShow()` flips to false (e.g. mouse-triggered mode + auto-hide) and re-attached at the latest position when it shows again. Modern browsers do not exit browser fullscreen on in-page clicks (only Esc does), so dragging works while fullscreen. The drag listener is attached once in `run()` on the reused clock node; it stays inert whenever the node is detached.
- `popup.html` / `popup.css` / `popup.js` — the extension popup, now a **「快速调整」subset**. `popup.html` loads `shared.js` then `popup.js`. The popup shows only: the live preview (sticky), an 外观 fieldset (字体大小 / 粗体 / 缩放 / 文字颜色 + swatches / 背景颜色 + swatches / 透明度), and a 显示 fieldset (仅全屏显示 / 常驻显示 + the `?` help bubble with active-state highlighting). A header button 「⚙ 更多设置」 and a bottom hint link both call `chrome.runtime.openOptionsPage()` to open the full settings page in a new tab. Writes to `chrome.storage.local` on every change (auto-save). For the two color fields the popup offers a row of one-click swatches plus a Hex text input (`colorHex` / `bgColorHex`, normalized to `#rrggbb`); each swatch only sets `color` or `backgroundColor`, so the swatch palette is a popup-only convenience over existing keys — it is **not** a new setting key and is intentionally not duplicated into `biclock.js` or `DEFAULTS`. There is no native `<input type="color">` color picker anywhere. The popup **no longer** hosts the 主题 grid, the 位置 panel, or the 保存为自定义主题 button — all of those moved to the options page. It does **not** write `customThemes` / `customHtml` / `posX` / `posY` / `clockStyle` unless the user actually edits a popup field, so it won't clobber a concurrent edit on the options page. The preview clock node carries `bpx-player-top-clock` so any inline `style` / `<style>` in the user's HTML template hits identically in popup preview, options preview, and the real on-page clock.
- `options.html` / `options.css` / `options.js` — the full **设置页 (options page)**, opened as a browser tab via `options_ui` (reached from the popup's 「更多设置」 button or the browser's extension-options entry — right-click icon → 选项 in Chromium, about:addons → BiClock → 设置 in Firefox). `options.html` loads `shared.js` then `options.js`. The page is a **three-column layout** (body `max-width: 1240px`): a left **分区导航** (`.options-nav`, sticky at `top:16px`, ~200px wide, AdGuard-style: no outer card border — sits flush on the page bg; each `.nav-item` is an icon glyph in a `.nav-icon` span + label, hover gets a `--surface-2` wash, and the active item gets a `--pink-soft` background, pink icon, bolder text, and a 3px pink bar — a left vertical bar in the side-column mode, switching to a bottom underline when the nav collapses to a horizontal tab strip at narrower widths — four anchor links `#sec-theme` / `#sec-appearance` / `#sec-html` / `#sec-about` pointing at the 主题 / 外观+显示 `.card-group` / 自定义 HTML 模板 / 关于 fieldsets; an `IntersectionObserver` scroll-spy in `options.js` `initNavSpy()` adds `.is-active` to whichever section is currently in the viewport's active band — older browsers without `IntersectionObserver` silently fall back to highlighting only the first item, anchor jumps still work via `<a href="#...">` + `scroll-behavior: smooth`), a middle scrolling **控制面板** (`.options-main`), and a right **预览栏** (`.preview-column`). The preview is a 16:9 `.preview-banner` whose background is a **pure-CSS reconstruction of the Bilibili player shell** (top bar with 圆形头像占位 / UP主名 / 粉色关注 button, a faint grid "video" region, and a bottom control bar with CSS-drawn play triangle / timecode / 粉色 progress fill / volume / fullscreen glyphs — all `aria-hidden="true"` decoration, no real assets), so the clock visually sits on a representative Bilibili player. The preview clock (`#previewClock`, `.bpx-player-top-clock`) is `position: absolute` inside the banner and **directly draggable** — clicking anywhere on the banner or dragging the clock sets `posX/posY` (the separate 位置 fieldset that used to exist has been removed; position control is now fused into the preview, and the same `posX/posY` is also live-editable by dragging the real clock on the Bilibili player — see the `biclock.js` bullet). Position math mirrors `biclock.js` exactly: `left/top` in % plus `transform: translate(posX*-100%, posY*-100%)` for edge-aligned semantics (posX=0 left-edge, 1 right-edge, 0.5 centered). The banner also carries a `实时预览` pill (top-left), a `拖动时钟调整位置` hint, and a 居中 reset button (`#resetPosition`, bottom-right). The middle column holds: the 主题 grid (the curated preset themes in `options.js` `THEMES` followed by the user's saved custom themes from `config.customThemes`; preset cards are immutable `<button>`s, custom cards are `<div role="button">` with ↻ 更新 / × 删除 inline action buttons and a double-click-to-rename name span) with a `theme-hint` line; a `.card-group` (grid `1fr / 1fr`) holding the 外观 fieldset (same fields as popup: 字体大小 / 粗体 / 缩放 / 文字颜色 + swatches / 背景颜色 + swatches / 透明度) and the 显示 fieldset (same as popup, with the `?` help bubble); the 自定义 HTML 模板 fieldset (`#sec-html`, class `css-fieldset` — the class name is historical; it carries all `.css-fieldset .docs` / `.css-input` / `.copy-btn` styling for the now-sole custom-code module; the fieldset `<legend>` is a `.template-legend` header holding the section title + a one-line description + the module-level 启用 toggle `<input id="customHtmlEnabled">` — the toggle lives in the legend because it gates the **entire** module, not just the textarea; below the legend is `<textarea id="customHtml">` + inline docs explaining the placeholder set `{{hh}}` / `{{mm}}` / `{{ss}}` / `{{time}}` + 2 copy-to-clipboard example cards 最简卡片 / 小狗抱时钟（SVG 装饰）; the fieldset is **collapsed by the `data-clock-disabled` hide rule** when 关闭时钟 is on, and the textarea+docs area (`.custom-html-content`) is **additionally hidden by a `.css-fieldset:has(#customHtmlEnabled:not(:checked))` rule** when the module toggle is off); and the 关于 fieldset (project blurb + single `about-meta` line with version / MIT / inline text links). A bottom `.bottom-actions` row holds the single primary button 「保存当前外观为自定义主题」 (`#saveCustomTheme`, `.primary-btn`) — it was moved out of the 主题 fieldset because it saves appearance **and** HTML template, so it belongs to the whole page, not the theme module. At `max-width: 1100px` the three columns collapse to two: the left nav stops being a sticky side column and becomes a horizontal tab strip (`flex-direction: row`, `grid-column: 1 / -1`) pinned above the control panel, while the preview column stays on the right; at `max-width: 920px` it further collapses to one column (nav tab strip on top, then preview, then control panel — preview no longer sticky); at `max-width: 620px` the `.card-group` also collapses. **Custom-theme semantics now include HTML template**: `saveCurrentAsCustomTheme()` / `updateCustomTheme()` snapshot the 13 `THEME_STYLE_KEYS` **plus** both `THEME_CSS_KEYS` (`customHtml` / `customHtmlEnabled`); `applyTheme()` restores them for custom themes, and for **preset** themes explicitly clears both (presets ship no HTML template). **HTML template submission is now explicit** (not per-keystroke auto-save): the `<textarea id="customHtml">` is a draft — typing only updates the syntax-highlight overlay and a `data-dirty="true"` flag on `.template-editor` + enables the bottom 「应用」 button (`#applyCustomHtml`, `.apply-btn`, disabled when the textarea matches `config.customHtml`); clicking 应用 commits the draft into `config.customHtml`, refreshes the preview, persists, and clears the dirty flag. A companion 「清除」 button (`#clearCustomHtml`, `.clear-btn`, on the same `.template-editor-actions` row, `margin-right:auto` so 应用 sits right and 清除 sits left; disabled when `config.customHtml` is empty) wipes only the applied template **content** — `config.customHtml = ''` + textarea cleared + `clockStyle = 'custom'`; it does **not** touch `customHtmlEnabled`, because the 启用 toggle is a module-level switch orthogonal to "is there template content" (an enabled module with an empty template naturally falls through to the built-in layout, since the HTML template gate is `customHtmlEnabled && customHtml`). Like 应用 it loses information (the applied template text), so it uses **two-step inline confirmation**: first click turns the button red with text 「确认清除？」 and arms a 3-second window (`data-confirm="true"`), a second click inside the window executes; timeout / click-elsewhere / Esc cancels (the cancel listeners are wired in `initClearButton()`). The 启用 toggle, by contrast, still saves immediately (it gates whether the module is active at all, so it must take effect instantly). Toggling 启用 flips `clockStyle='custom'` (the `onInput` ids list contains `customHtmlEnabled`); clicking 应用 or 清除 also flips `clockStyle='custom'`. `updateClearButtonState()` (called from `fillForm()` and the starter-template path) recomputes the 清除 button's `disabled` from whether `config.customHtml` has content; `applyTheme()` → `fillForm()` keeps it in sync across preset/custom theme switches. `options.css` is **self-contained** (own `:root` tokens copy, does **not** import `popup.css`). Copy buttons use `navigator.clipboard.writeText` with a 「✓ 已复制」 flash and a fallback to selecting the code text. `options.js` is effectively the pre-split `popup.js` plus the copy-button logic and the left-nav scroll-spy (`initNavSpy()`, whose `sectionIds` array is `['sec-display', 'sec-theme', 'sec-appearance', 'sec-html', 'sec-about']` — `'sec-css'` was removed when the CSS fieldset was deleted); the swatch / Hex / preview / form helpers are deliberately duplicated between `popup.js` and `options.js` rather than extracted into a shared module, because the two pages have subtly different field sets and side effects (the popup, for instance, does not read or write `customHtml` / `customHtmlEnabled` at all — it only mirrors them so its preview reflects the real clock under both styling modes).
- `icons/clock.png` — extension icon (size 200).
- `shot.mjs` + `popup-shot.png` / `options-shot.png` — Playwright script that regenerates the two README screenshots and its output PNGs. **Dev-only artifacts** (not part of the runtime package — `package.mjs` INCLUDE list intentionally excludes them, same as `README.md` / `AGENTS.md` / `node_modules`). The PNGs are committed so the README renders on GitHub without a build step. See Commands below for how to run it and Conventions for the "re-shoot after UI change" rule.

## Commands

There is no package manager and no `package.json` deps (the file exists only for repo metadata). Two plain-Node helper scripts live at the repo root:

- `node package.mjs` — zips the runtime files (`manifest.json`, `shared.js`, `biclock.js`, `popup.html`, `popup.css`, `popup.js`, `options.html`, `options.css`, `options.js`, `icons/clock.png`) into `BiClock-<manifest-version>.zip`, with files at the archive root (no nested folder) for store upload. Cross-platform: prefers system `zip`, falls back to `tar` (Windows ships bsdtar as `tar.exe`); `--force-local` is passed to `tar` so Windows drive letters like `D:` aren't parsed as rsh-style hosts. Missing any file in the INCLUDE list fails the script fast.
- `.github/workflows/release.yml` — on pushing a `v*` tag, verifies the tag matches `manifest.json` `version`, runs `node package.mjs`, and creates a GitHub Release with `BiClock-<version>.zip` attached; the Release body is auto-generated from commits between the previous tag and this one. Tag must equal the manifest version or CI fails fast.
- `node shot.mjs [popup|options|all]` — regenerates the README screenshots `popup-shot.png` and `options-shot.png` (default `all` does both) by loading `popup.html` / `options.html` in Playwright Chromium and capturing a full-page screenshot. **The screenshots must stay in sync with the actual UI.** The script injects a pure-in-memory `chrome.storage.local` / `chrome.runtime` mock via `page.addInitScript` *before* each page loads — without it, `popup.js` / `options.js` `init()` throws on `chrome.storage.local.get(...)` under `file://` (the `chrome` global doesn't exist outside an extension), so no form is filled, no swatches are built, and the preview clock never gets its inline styles, which is exactly why the old popup screenshot looked nothing like the real popup. The mock makes `init()` run end-to-end, so the screenshot equals the real rendered page. Output paths are derived from the script location (cross-platform, no hardcoded drive letter). Depends on the dev-only `playwright` in `node_modules`; if the Chromium binary is missing, run `npx playwright install chromium` first.

To test changes locally:

1. Load the folder as an unpacked/temporary extension (chrome://extensions in dev mode, or `about:debugging` → This Firefox → Load Temporary Add-on).
2. Open any Bilibili `/video/` or `/bangumi/` page, enter the player, **enter browser fullscreen**, and move the mouse to show controls — with defaults (仅全屏显示 on, 常驻显示 off) the clock appears centered at the top only while both `data-screen="full"` and `data-ctrl-hidden="false"`.

There is nothing to typecheck or lint; review changes by reading the file. `node --check <file.js>` catches syntax errors for the four JS files (`shared.js`, `biclock.js`, `popup.js`, `options.js`).

## Architecture & coupling notes

- `biclock.js` is tightly coupled to Bilibili's current player DOM. It queries specific class names that can change when Bilibili ships a player update:
  - `.bpx-player-container` — the element observed for control visibility and screen mode.
  - `.bpx-player-top-left` — the sibling the clock is inserted after.
  - Attribute `data-screen` on `.bpx-player-container` — `"full"` means true browser fullscreen (Fullscreen API). Only this mode hides Bilibili's/browsers' own floating video toolbars, so by default (仅全屏显示 on) the clock is shown **only** when `data-screen="full"`. When the user turns 仅全屏显示 off, this attribute is ignored and the clock shows in any screen mode (normal, wide, web, full) — the user accepts coexisting with those overlays. Wide (`"wide"`) and web fullscreen (`"web"`) modes are otherwise intentionally excluded.
  - Attribute `data-ctrl-hidden` on `.bpx-player-container` — `"false"` means controls visible. In the default **mouse-triggered** mode (`alwaysShow=false`), this must be `"false"` for the clock to show. In **always-on** mode (`alwaysShow=true`) it is ignored. `shouldShow()` is the single gatekeeper; it first applies the `fullscreenOnly` gate, then the `alwaysShow` gate.
  - The older `bilibili-player` (`.bilibili-player-`) class prefix is **not** handled; only the current `bpx-player-` prefix is. If the clock stops appearing, the first thing to check is whether Bilibili renamed these classes.
- A `MutationObserver` watches attribute changes on `.bpx-player-container`; the 1-second `setInterval` is started only when `shouldShow()` is true and stopped otherwise. `shouldShow()` requires `data-screen="full"` only when `fullscreenOnly` is on; it additionally requires `data-ctrl-hidden="false"` unless `alwaysShow` is on. `stopTimer()` also detaches the clock node from the DOM so it doesn't linger when it shouldn't show. Don't introduce a second always-running interval — keep it tied to `shouldShow()`. Display-setting switches (`fullscreenOnly` / `alwaysShow`) arrive via `chrome.storage.onChanged` (not a player attribute), so the change handler re-runs `shouldShow()` and starts/stops the timer immediately.
- `updateClock()` re-inserts the clock node on every tick. The clock node is reused (same reference), so this moves rather than duplicates it; if you change this, preserve the "single reused node" invariant to avoid stacking duplicates. It is always appended to `.bpx-player-container` (both display modes). The node is positioned with `position: fixed` relative to the **player container's viewport rect** (`getBoundingClientRect`), not relative to the viewport as a whole — the player does not fill the viewport in non-fullscreen modes (Bilibili chrome takes up the top/sides), so a viewport-relative `posX/posY` ratio would place the clock outside the video. Container-relative coordinates keep the clock inside the video across normal/wide/web/fullscreen modes. Mounting on the container (rather than inside the top bar) also avoids the CSS transform/contain trap where a `fixed` descendant is re-anchored to a transformed ancestor; the container is a stable host. `.bpx-player-top-left` is no longer used as a mount point.
- Styling is applied via a **two-mode** path: **HTML template mode** (gate `customHtmlEnabled && customHtml`) and **inline mode** (default, when the gate is false). **Inline mode**: appearance is applied imperatively via `clock.style.*` on every tick — no injected CSS file, no shadow DOM. **HTML template mode**: `applyStyles()` walks `APPEARANCE_INLINE_KEYS` (a shared.js constant — `color, backgroundColor, fontWeight, fontFamily, fontSize, textShadow, border, padding, borderRadius, boxSizing`) and calls `removeProperty` on each, so the user's HTML template (inline `style` / `<style>` included) becomes the **sole** source of appearance and **no `!important` is needed** to override the built-in look; `renderClockLayout()` then dispatches to `applyHtmlTemplate(el, html, time)` instead of any built-in layout branch. The HTML template re-render contract is **distinct** from inline mode: the built-in layout branches (single / segments / analog / flip / etc.) call `el.replaceChildren()` on every tick; `applyHtmlTemplate` **only rebuilds the subtree when the `customHtml` string changes**, tracked via `el._biclockLastHtml`. On each 1-second tick where the template is unchanged, it only walks the cached `el._biclockParts` span references (collected by `splitPlaceholders` during the last rebuild — `<span data-biclock-part="hh|mm|ss|time">` nodes, with duplicates supported) and updates their `textContent`. This means template 装饰 elements (a drawn dog, an SVG frame, decorative containers) survive across ticks — they are not wiped and redrawn every second. Placeholders are recognized by walking text nodes with `document.createTreeWalker` and splitting on `/\{\{\s*(hh|mm|ss|time)\s*\}\}/i`; non-matching `{{...}}` is left as literal text, and surrounding text in the same text node is preserved (so `现在是 {{hh}} 点` doesn't lose its `现在是` / `点`). Position (`position/left/top/transform/zIndex/userSelect`) is always JS-computed in both modes (so the options-page drag panel keeps working); complex-layout DOM for the built-in modes (analog dial hands, flip cards, etc.) is always JS-rendered (those child coordinates can't be rebuilt in CSS) — HTML template mode is the only mode where the user authors the entire subtree. Because `updateClock()` re-runs `applyStyles()` every tick, switching the 启用 toggle or clicking 应用 re-cleans/re-applies inline each second — no flicker, no stale inline leak; `applyHtmlTemplate`'s diff also means each committed template change triggers exactly one subtree rebuild (the subsequent ticks within the same template are text-only updates). Typing into the HTML textarea no longer commits per keystroke — the draft only becomes `config.customHtml` when the user clicks 应用 (see the `options.html` bullet), so the per-character rebuild happens at most once per 应用 click, not per keystroke. (The popup has its own `popup.css` and the options page has its own `options.css`, but the on-page clock follows this two-mode rule.) There is no separate user-CSS injection path anymore — the previous `<style id="biclock-custom-css">` element in `biclock.js` and the matching `<style id="preview-custom-css">` in popup/options were removed when the custom CSS mode was deleted; users who want CSS-only effects now write `<style>` directly inside their HTML template. Both preview clock nodes (popup and options) carry `bpx-player-top-clock` and both `refreshPreviewText()` calls pass prefix `'bpx-player-clock'` (theme-card samples still use `'clock'` to stay isolated). The options page is the only place that *edits* `customHtml`; the popup still mirrors it so its preview stays consistent with the real clock under both modes. Note: HTML templates are parsed via `<template>.innerHTML`, so any `<script>` in the template does **not** execute (browser standard for `template.content`); `<img>` and similar tags **do** fire real network requests, which is the user's responsibility to manage.
- User styling flows through `chrome.storage.local`. `popup.js` and `options.js` both write settings on every input event (auto-save, no Save button); `biclock.js` reads them at startup and subscribes to `chrome.storage.onChanged` so changes from **either** UI take effect on an already-open Bilibili tab without a reload. The popup and the options page never message each other directly — they coordinate purely through storage (the popup re-reads storage every time it opens, and `chrome.storage.onChanged` is the only cross-page channel the content script needs). Because both UIs can be open at once, avoid writing keys you didn't read from a control: `popup.js` deliberately calls `save()` only after a real field edit, so it won't overwrite `customThemes` / `customHtml` / `posX` / `posY` changes made concurrently on the options page. The popup's 「更多设置」 button and bottom hint link both call `chrome.runtime.openOptionsPage()` (the standard MV3 entry; do **not** use a `web_accessible_resources` + manual-tab approach — `options_ui` registration also gives you the browser's built-in options entry).
- `DEFAULTS` lives in `shared.js` as the single source of truth for default values — it is no longer duplicated, so changing a default or adding a field is a one-file edit. The keys are: `fontSize`, `clockScale` (overall scale factor applied via CSS `transform: scale()`, default `1` = no scaling; range exposed in the UI is 0.5–2 with 0.05 steps. This is the **only** way to resize a custom-HTML-template clock, because the template's hardcoded `px` / `em` sizes can't be rewritten by JS — `scale()` uniformly grows/shrinks the entire subtree including the template, the close button, and all built-in layouts. It is composed with the positioning `translate()` as `translate(posX*-100%, posY*-100%) scale(clockScale)` in `biclock.js` `applyStyles()` and `options.js` `updatePreviewPosition()` (translate first, then scale — CSS applies right-to-left, so scale doesn't distort the translate's self-relative percentages); the popup preview doesn't participate in drag positioning, so `popup.js` `applyToPreview()` writes a standalone `transform: scale(clockScale)`. Because `scale()` is a pure visual transform that doesn't affect layout-box size, the drag math in `setPositionFromPointer()` (both `biclock.js` and `options.js`) measures the clock via `getBoundingClientRect()` (post-scale rendered size) rather than `offsetWidth/Height` (pre-scale layout size), so the `spanX/Y = container - ownSize` calculation and the `grabOffset` anchor stay consistent under any scale — otherwise dragging at `clockScale ≠ 1` would feel laggy/off. The 缩放 row in both popup and options carries a small inline 「重置」 button (`#resetClockScale`, `.reset-inline-btn`) next to the percentage readout — `updateResetClockScaleState()` (called from `fillForm()` and `onInput()`) disables it while `clockScale === 1` (so default state shows a greyed-out button, making it visually obvious when the user has drifted from 100%) and enables it the moment the slider moves; clicking it sets `clockScale = 1`, marks `clockStyle = 'custom'` (same as any other appearance edit), refreshes preview + persists), `color`, `backgroundColor`, `bgOpacity` (0–100), `bold`, `fullscreenOnly` (scope gate: true = browser-fullscreen only, the default; false = show in any player screen mode), `alwaysShow` (display mode within that scope: false = mouse-triggered, true = always-on), `posX`/`posY` (clock position as a 0–1 ratio of the **player container's** width/height, **edge-aligned**: `(posX, posY)` is where the clock's top-left corner lands — `0/0` puts it at the container's top-left, `1/1` puts its bottom-right at the container's bottom-right, `0.5/0.5` is centered; position is set either by dragging the clock in the options-page preview banner, or by dragging the clock directly on the real Bilibili player — both write the same `posX/posY` keys via `chrome.storage.local`, so the two surfaces stay in sync; there is no separate top-offset knob), `customThemes` (an array of user-saved custom themes; default `[]`; **only the options page reads or writes it** — the content script never consumes it, so adding/removing custom themes has zero effect on the running clock unless one becomes the active `clockStyle`), and `customHtml` / `customHtmlEnabled` (user-supplied HTML template containing `{{hh}}` / `{{mm}}` / `{{ss}}` / `{{time}}` placeholders; default `''` / `false`). Each custom theme element is `{ id, name }` plus the 13 `THEME_STYLE_KEYS` **and** the 2 `THEME_CSS_KEYS` (`customHtml` / `customHtmlEnabled`) — saving a custom theme snapshots the current HTML template alongside the appearance, and applying that theme restores both; preset themes carry no HTML template and applying one clears both keys. `id` is `"custom_<timestamp>"` and is also stored in `clockStyle` when that theme is active, `name` defaults to `"自定义 N"` (auto-numbered to avoid colliding with already-renamed cards) and is editable via double-click on the card name. Background color is stored as `#rrggbb` plus a separate `bgOpacity` percentage; the default `backgroundColor` is `#fb7299` (Bilibili pink), with `color` defaulting to `#ffffff`. Both popup and content script convert to `rgba()` via the shared `hexToRgba()` helper. The time format is hardcoded to 24-hour with seconds (`HH:MM:SS`) and is no longer configurable, so neither `use24Hour` nor `showSeconds` exists as a setting.

## Conventions

- Vanilla JS, `var`/`function` style, browser globals only — no modules, no imports. Match this style for the content scripts (`shared.js`, `biclock.js`); they run as classic scripts whose top-level `var`/`function` declarations share one global, so `biclock.js` may reference symbols defined in `shared.js` purely by load order (manifest's `content_scripts.js` array is `["shared.js", "biclock.js"]`).
- Keep all DOM queries defensive: Bilibili pages are SPA-driven, so elements may not exist yet. `run()` currently assumes `.bpx-player-container` is present at `DOMContentLoaded` / on script run; if you add features, re-query at use time rather than caching long-lived references.
- **Keep the README screenshots in sync with the UI.** Any change to `popup.html` / `popup.css` / `popup.js` or `options.html` / `options.css` / `options.js` (and any `shared.js` change that affects the rendered preview — `DEFAULTS`, `THEMES`, `renderClockLayout`, the swatch palettes) must be followed by re-running `node shot.mjs` (regenerates both `popup-shot.png` and `options-shot.png`) and committing the updated PNGs in the same commit as the source change. The screenshots are how the README sells the extension, so a stale shot that drifts from the real UI is a bug. Do not hand-edit the PNGs; the script is the single source. If you change the popup/options viewport contract (e.g. body width, three-column breakpoints), also revisit `shot.mjs`'s hardcoded viewport sizes (`320×800` popup, `1280×900` options) so the shot still frames the page the way a real user sees it.
